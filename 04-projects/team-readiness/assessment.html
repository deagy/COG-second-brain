Readiness assessment · 2026-09-02

Four tools, one team

Whether cadre, the lifecycle kernel, recall and gloop can be handed to an internal team today — and if not, what stands in the way.

cadre 5976dd2d · cadre-kernel c9500b6 · recall 6961d3e · gloop 9f0f9b9
All four green on CI. Evidence gathered by clean-container install, live commands against built binaries, and the GitHub API.

Not yet — but the gap is smaller than it looks.

Nothing here is unsound. The code is well tested, the install works, and the parts that were built carefully were built very carefully. What is missing is almost entirely the difference between one operator who knows everything and a colleague who knows nothing.

That is not an accident, and it is worth saying plainly: the readiness work that closed this morning was chartered against a stated bar — “your own multi-agent work, run daily. One operator.” Two of its decisions were justified by that fact. Both expire the day a second person logs in.

What stops a colleague in their first hour

These were found by installing into a clean container as someone who has never seen the repositories, following only what the docs say. Each is cheap to fix; together they are the difference between “this works” and “this works for me.”

The first real task needs an interactive login blocker

Installing succeeds. Then the entire point — dispatching work across the specialist roles — stops dead. There is no headless or CI path documented anywhere.

$ echo "" | claude -p "say hi" Not logged in · Please run /login

Worse for a newcomer: a typo'd or expired key does not fail. It hangs, silently, with no output for over ninety seconds and then exits 0. Someone debugging that alone will not get there.

The documented first command cannot be typed friction

The install line is curl … | sh, on an image with no curl, no git and no python3. INSTALL.md says the script needs git and Python — it does not say they may be absent, and it never mentions needing curl to fetch the installer at all.

$ docker exec cadre-test which git python3 curl exec: "git": executable file not found in $PATH exec: "python3": executable file not found in $PATH

Then cadre is not on PATH. The installer prints a note about it after finishing; a reader who skips that line gets command not found on the very next documented step.

Three of four front pages send a newcomer nowhere friction

cadre's README opens with a “Choose your path” table linking six documents — docs/INSTALL.md is not among them; its only two links sit further down inside a runner table. cadre-kernel has no README at all. recall has no installation section, and never tells the reader that prebuilt binaries for six platforms exist on its releases page.

Nothing explains how the four fit together blocker

This is the largest documentation gap and the one no individual repo owns. cadre's README and IDENTITY.md never mention recall or gloop. recall never mentions cadre. What exists is four one-directional pointers, each visible only from inside the dependent repo — including the sole statement of the cadre↔recall relationship, buried three directories deep in a subsystem README.

No document anywhere gives an adoption order. A team would have to derive it.

Eighteen documentation claims are still false or dangling friction

Counted, not sampled: nine in cadre, three in the kernel, five in recall, one in gloop. The sharpest are a README that asserts both that the kernel lives in-repo and that it does not; a kernel document citing a reference provider file that does not exist; and <subcommand> --help documented as the way to discover options while failing for 27 of 30 subcommands.

What changes when there are N of you

Two properties were correct under one operator and stop being correct with a team. Both are recorded honestly in the code's own SECURITY.md — neither is a surprise, and neither has been fixed because until today it did not need to be.

The audit trail cannot tell two people from one blocker

Actor fields are caller-supplied text. Separation of duties is enforced by comparing two strings for equality. A single process, one keyboard, staged a record as one person and approved it as another — both accepted, with a byte-identical observed actor on each row.

staged_by "alice@example.com" observed_actor "os:deagy git:test@example.com" decided_by "bob@example.com" observed_actor "os:deagy git:test@example.com" → accepted

The charter's reasoning was “with one operator there is nobody to impersonate.” With a team, an approval record that names a person nobody verified is a record of a string.

You cannot honour a deletion request blocker

retention-report, delete-ingested and deletion-evidence existed in the Python CLI and were never rebuilt. Nothing records a retention window at ingest, nothing ages out, and no shipped command can remove ingested content — only still-staged proposals, which are properly handled with durable evidence.

The charter accepted this because “no third party's content enters the store.” A colleague's notes are a third party's content.

There is no shared store, and the sharing bug already happened once friction

A store is a local SQLite file — project-local or global, both plain paths, with no sync, server or replication in the path cadre uses. Issue #249 was exactly this hazard realised: the tier walk conflated project-local and global, a write landed in the shared store, and reversing it needed an authorised deletion.

Separately, recall's own store sets its pragmas per-connection with no busy timeout and no retry — the precise pattern cadre already had to fix in its staged store after two concurrent writers hit database is locked. It has not been load-tested. Two people sharing a store is when it would bite.

What is already strong enough to build on

Worth stating, because the roadmap below should not accidentally rebuild any of it.

The finding that shortens everything below: recall already ships recall-server as a released binary on six platforms, with API-key, namespace-scoped and JWT authentication behind 37 tests — and its Authenticate returns a subject, which is precisely the verified identity the actor fields lack today.

cadre never wires to it; internal/retrieval opens a local file directly. So multi-user identity and a shared store are mostly an integration of something that already exists, not an auth system to design.

Roadmap

P0

Make the first hour survivable

days · docs only

Nothing here needs code. It is the difference between a colleague succeeding and quietly giving up.

  • Document the claude authentication step, including a headless path — or state plainly that an interactive login is required and there is no CI story yet.
  • List every prerequisite before the first command: curl, git, Python 3.10+, Go and its version, network egress, and the PATH entry.
  • Put an install link in cadre's “Choose your path” table. Give cadre-kernel a README. Give recall an installation section that names its released binaries.
  • Set the GitHub description on cadre, recall and gloop — three of four are blank, and it is the first thing anyone sees.
  • Fix the eighteen counted false or dangling claims, starting with cadre's README contradicting itself about where the kernel lives.
P1

One page that explains the four together

days · one document

The single highest-value artifact that does not exist. It needs to say what each tool is for, that the kernel records and validates while cadre drives, that recall is the knowledge backend both cadre and gloop use independently, and what order to adopt them in.

  • One overview, linked from all four front pages, not a fifth scattered pointer.
  • A glossary: roster, catalog, routing, dispatch plan, gate, G1–G10, provider, lane, kernel. A newcomer currently has to find each definition in a different repository.
P2

Make the record mean something with more than one person

weeks · integration

Either close the identity gap or scope the claim down — but do not leave an approval trail that reads as authoritative while being unverified.

  • Derive the recorded actor from an authenticated subject. recall-server's Authenticate already returns one; the work is wiring cadre's retrieval and knowledge paths to it rather than to a local file.
  • Compare the observed actor against the asserted name — today it is written and never consulted by any check.
  • If that is more than you want to spend now, the honest alternative is to say in the tool's own output that actor fields are unverified, so nobody builds a process on them.
P3

Retention and erasure, for real

weeks
  • Record a retention window at ingest, so something can age out.
  • Rebuild delete-ingested and deletion-evidence against recall's library delete, which exists but is reachable only by writing Go.
  • Load-test recall's store under two concurrent processes, and give it the connection-string pragmas and busy-retry that cadre's staged store already has.
P4

Decide about gloop

a decision, then days

This one is yours and nothing else depends on it. Three coherent options:

  • Leave it out of the team story. Cheapest and currently true — it is private, unreleased, and nothing imports it.
  • Share it internally. Grant collaborator access (no teammate has any today), add a licence, and decide whether tags produce releases. Its go.mod also pins recall v0.1.0 against a shipped v0.3.3 — a real release, so not broken, but three minors behind.
  • Fold it in. If gloop is genuinely the runtime for cadre's plans, that relationship deserves to exist in code and documentation rather than in one sentence of gloop's README.

If you want the short version

Ship recall now — it is licensed, released, has zero broken links, and needs an installation section. Ship cadre and the kernel after P0 and P1, which are days of documentation, not engineering. Hold the knowledge store's approval workflow until P2, or tell people plainly that its actor names are unverified. Decide about gloop separately, because nothing waits on it.

The thing not to do is hand over all four today and let a colleague discover the login wall, the blank front page and the unverified approval trail on their own — because each of those reads as “this tool is broken” rather than “this tool has not been introduced yet,” and first impressions of internal tooling are difficult to re-earn.
