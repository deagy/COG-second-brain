# Multi-user readiness: cadre, cadre-kernel, recall, gloop

Scope: `cadre knowledge` actor identity, store location, concurrency, retention/erasure, secrets. All commands run against a fresh project-local store at `/tmp/claude-1000/multiuser-test` (git repo with `.agents/knowledge-store/config.json` = `{}`), built from `~/sdk/cadre` with `CGO_ENABLED=1 go build -tags sqlite_fts5 -o /tmp/claude-1000/cadre-bin ./cmd/cadre` (exit 0). Environment during the run: `whoami` = `deagy`, `git config --get user.email` = `test@example.com` (both global).

## Depends on there being one operator

**Actor fields are unauthenticated strings; the only real identity check is process/git identity, which is one identity for however many people share the machine.** `~/sdk/cadre/internal/platform/identity.go:81-97` (`ObserveActor`) reads `os/user.Current()` and `git config --get user.email` — both properties of the machine/checkout, not of a session or a login. Every `--staged-by`/`--decided-by`/`--deleted-by`/`--authorized-by` value is caller-supplied free text (`roster/knowledge-store/SECURITY.md:29,54,58,60`). Live proof: I staged a record with `staged_by: "alice@example.com"`, then dispositioned it with `decided_by: "bob@example.com"` — both calls ran as the same OS process/user. `show-staged` recorded `"observed_actor": "os:deagy git:test@example.com"` identically on both the stage and the disposition rows, while the asserted names differed and were accepted (`cadre knowledge propose --from-finding finding-alice.json` → staged; `cadre knowledge disposition-staged -decided-by bob@example.com` → accepted). The self-approval guard only catches the case where the two asserted strings are *equal*: running `disposition-staged -decided-by "alice@example.com"` (same string as `staged_by`) on the same record was refused with `error: "alice@example.com" staged this record and cannot also disposition it` — but this is a string-equality check, not an identity check, exactly as `SECURITY.md:60` states ("compare two caller-asserted strings, authenticated by nobody... an actor that stages as one name and decides as another satisfies both"). One person at one keyboard can pose as two people to satisfy separation-of-duties; the record cannot tell the difference between that and two real people, because `observed_actor` is never compared to the asserted names by any check (`SECURITY.md:62`: "recorded on deletion, not consulted by any check").

**The shared-machine credential story generalizes past the knowledge store.** GitLab writes go through one service token, `GITLAB_SVC_TOKEN` (`~/sdk/cadre/internal/orchestration/gitlab.go:60`, also `~/sdk/cadre/internal/cli/config.go:10`), scoped operationally to one dedicated docs project (`~/sdk/cadre/internal/config/registry.go:21-27` comment). If several people share a machine/environment with this variable set, every GitLab write is attributed to the one service account, same gap as the knowledge-store actor fields — there is no per-person credential in this design at all, by design, not by oversight (comment explicitly frames it as containment, not per-caller attribution).

**The retrieval store is hard-wired to a local file, with no server in the path cadre actually uses.** `~/sdk/cadre/internal/retrieval/store.go:127` opens `store.NewSQLiteStore(...)` directly — no URL, no auth, no network hop. `grep` for `NewServer`/`ListenAndServe`/`client.New` anywhere under `~/sdk/cadre` returned nothing. So even though the underlying `recall` library ships an HTTP server (see below), cadre's own CLI never uses it — `cadre knowledge search`/`propose`/etc. always mean "open this file on this machine."

## Safe for a team as-is

**Concurrent writers to the staged store do not corrupt or lose data.** `~/sdk/cadre/internal/knowledge/staged_db.go:58-61` (`dsn`) sets `busy_timeout`, `journal_mode=WAL`, and `foreign_keys=on` as connection-string pragmas (not per-connection `Exec`, which the comment at lines 50-57 explains was a prior bug: "a busy_timeout set that way is absent on the next connection... two concurrent writers failed with 'database is locked'"). `execWithBusyRetry` (`staged_db.go:109-125`) retries schema-init lock contention with backoff up to `BusyTimeout` (5s, line 48). Live test: 6 parallel `cadre knowledge propose --from-finding ...` processes launched simultaneously against the same store all succeeded (exit 0, all returned `"status": "staged"` with distinct ids `KS-20260902-concurrency-probe-1..6`). `list-staged` afterward showed all 7 records (6 concurrent + 1 earlier) present — no lost writes, no lock errors, no corruption.

**Deletion of staged (not-yet-ingested) records is a real, evidence-tracked operation, safe for a team to rely on for that narrow case.** `cadre knowledge delete-staged -id ... -deleted-by ... -reason ...` actually removed the record (`show-staged` afterward: `error: ... no staged record with that id in this store`) and wrote a row to `staged_record_deletions`, readable back via `deletion-evidence-staged` (`SECURITY.md:46`, confirmed live: the evidence row carried `deleted_by`, `observed_actor`, `status_at_deletion`, `reason`, timestamp). The evidence table has no foreign key to the record it describes, specifically so the evidence outlives the deleted subject (`SECURITY.md:46`).

**Secrets are never written to disk by either tool, and this is enforced, not just conventional.** `~/sdk/cadre/internal/config/files.go:30-46` rejects any config key shaped like `token`, `*_token`, `api_key`, `password`, `secret`, `svc_token` before it is read from or written to any `cadre.yaml`/`config.yaml` file — this is a hard `settingsErrorf`, not a lint. `~/sdk/cadre/internal/config/resolver.go:9-15` states the same as a package-level guarantee. gloop mirrors the pattern: `~/sdk/gloop/pkg/config/config.go:112-114` (`KnowledgeConfig.APIKeyEnv`) and the equivalent `ProviderConfig`/`ProviderEntryConfig` fields (lines 226, 315) store only the *name* of an environment variable, never a key value; `~/sdk/gloop/pkg/config/save.go:14-26` writes an explicit header into every generated TOML file stating keys are not persisted; `~/sdk/gloop/pkg/config/redact.go` redacts config for display by construction (only names/env-var-names ever enter the map); `~/sdk/gloop/pkg/redact/redact.go:44-58` additionally pattern-matches and masks stray secret-shaped strings (Anthropic/OpenAI/Google key shapes) in arbitrary text. Live confirmation: `os.Getenv(cfg.Provider.APIKeyEnv)` is the only read path in `~/sdk/gloop/cmd/gloop/cmd/setup.go:99-102` and `~/sdk/gloop/gloop/knowledge/embedder/openai.go:159`. Because the key only ever exists in the process environment and is never cached to a shared file, one credential-hygiene mistake this design does prevent is "the key ends up committed or synced in a config file."

## Unclear, and what would settle it

**Whether "one shared store, several people" is meant to work at all is answered for storage location but not for intent.** `~/sdk/cadre/internal/platform/paths.go:83-155` (`FindFileAtProjectRoot`) and `roster/knowledge-store/SECURITY.md:11-17` establish the two tiers precisely: project-local (`.agents/knowledge-store/config.json`, walking up to `.git`) or global (`$KNOWLEDGE_STORE_HOME`, default `~/.agents/knowledge-store/`), both plain local paths — there is no sync, replication, or shared-server config surface for either tier in the code I read. `paths.go:89-99` even documents a real incident (issue #249) where the walk conflated the two tiers and a write landed in the wrong (shared) store, needing an "authorized deletion" to reverse — i.e., the two-tier design has already produced one cross-contamination bug in practice, which is evidence against, not for, casual multi-person/multi-project sharing of the global tier. What would settle it: an explicit statement (I found none) of whether `~/.agents/knowledge-store` is meant to be one operator's home directory only, or is expected to be synced/shared across a team's machines by some external mechanism (e.g., a shared network home, dotfiles sync) that the codebase itself is silent on.

**`recall` (the storage engine cadre depends on) has a real client/server/auth story that cadre does not use.** `~/sdk/recall/api/server.go` and `~/sdk/recall/api/README.md` describe a working HTTP API (`NewServer`, `ListenAndServe`) with pluggable authentication — static API keys (`APIKeyAuth`), per-key namespace scoping (`ScopedAPIKeyAuth`), and JWT (`JWTAuth`) — and a separate `recall-server` binary (`~/sdk/recall/cmd/recall-server/main.go`) that runs it standalone. The `recall` CLI itself supports `--server <url>` / `cli.url` to talk to a running server instead of a local file (`~/sdk/recall/cmd/recall/root.go:41,61,124,146`; some subcommands explicitly refuse in this mode: `local.go:116,176`, "this command is local-only... rerun without --server"). This means genuine multi-user/multi-machine sharing with per-caller authentication is *architecturally possible* on top of recall today — but nothing in cadre's `internal/retrieval` or `internal/knowledge` wires it in (confirmed: no `NewServer`/`client.New`/`--server` reference anywhere under `~/sdk/cadre`). Whether recall's server mode is production-hardened (rate limits, key rotation, audit logging tied to the API-key identity rather than a caller-asserted string) I did not verify — that would settle whether "point cadre at a shared recall-server instead of a local file" is a real near-term option or requires more work than the client flag suggests.

**Concurrency on the retrieval-side store (recall's `SQLiteStore`, used by `cadre knowledge search` and `recall upload`) has weaker protection than the staged store's, and I did not load-test it.** `~/sdk/recall/store/sqlite.go:53-63`: `db.SetMaxOpenConns(1)` and `PRAGMA journal_mode=WAL` are set via `db.Exec`, the same per-connection pattern that `~/sdk/cadre/internal/knowledge/staged_db.go:50-57`'s comment identifies as the exact bug pattern that caused "database is locked" for the staged store before it was fixed with connection-string pragmas. I found no `busy_timeout` pragma and no retry-on-`SQLITE_BUSY` logic anywhere in `~/sdk/recall/store/sqlite.go` (`grep` for `busy_timeout|SQLITE_BUSY|database is locked|retry` returned nothing). `SetMaxOpenConns(1)` serializes concurrent access *within one process*, but says nothing about two separate OS processes (e.g., one person running `recall upload` while another runs `cadre knowledge search`) opening the same file at once — SQLite's own locking would apply, but with no configured busy_timeout a lock collision returns `SQLITE_BUSY` immediately rather than waiting, and nothing here retries it. I did not run a live concurrency test against this store (would need a working recall config + embedder, which was out of scope for the time available); the file:line evidence establishes the code shape but not the observed failure mode under load. What would settle it: launch two concurrent `recall upload`/`recall search` processes against the same SQLite file the way I did for the staged store, and see whether either fails with a locked-database error instead of retrying.

**Retention/erasure of ingested (not staged) content is a declared gap, not a partial implementation — but I did not verify recall's low-level delete API actually works, only that no CLI exposes it.** `roster/knowledge-store/SECURITY.md:38-44` states plainly: `cadre knowledge ingest`, `retention-report`, `delete-ingested`, and `deletion-evidence` "were real, tested commands in the Python CLI and were removed in `b418031e`... None was rebuilt." Live confirmation: all three retired verbs fail with an explicit message naming the gap (`cadre knowledge retention-report` → "shipped in the Python CLI, removed... per-message retention windows were a Python-era capability; this binary records none"; `cadre knowledge delete-ingested` → "deleting ingested content... is not a capability this binary has... recall's own CLI exposes no delete command either, so this is a library call, not something to run"; `cadre knowledge ingest` → "retired... run `recall upload`"). So: no retention window is ever recorded at ingest time, nothing ages out, and there is no CLI-level way for a steward to honor a deletion request against ingested content — only against still-staged (not yet ingested) proposals. `SECURITY.md:38` says recall's Go API "deletes by document or chunk id," which I did not call directly (it's a library function, not a CLI command) — so "can a person's content be deleted from the store on request" is technically "yes, by someone willing to write Go against `recall`'s store package," and "no" for anyone using only the shipped CLIs. That distinction matters for a team readiness call and I did not verify the library-level delete actually works end-to-end.
