# Readiness Assessment: Could a Newcomer Learn These From the Docs Alone?

Repos: `~/sdk/cadre`, `~/sdk/cadre-kernel`, `~/sdk/recall`, `~/sdk/gloop`. Read-only audit; nothing under `~/sdk` was edited. Evidence gathered by four parallel repo-scoped audits plus direct cross-repo checks; every command/path claim below was executed or `git ls-files`/`ls`-verified, not inferred from prose.

## Entry points, per repo

**cadre** — `README.md`'s first substantive sentence states purpose before any command: *"A secure cloud agent suite for teams building self-hosted infrastructure and applications with Proxmox, Talos, Kubernetes, Helm, OpenTofu, GitLab CI/CD, Go, PostgreSQL, React, TypeScript, Python where useful, and Gherkin-based integration/regression testing."* Good ordering. But `docs/README.md` (the doc index) opens with *"Use this index to choose the shortest useful path"* — a navigation statement with zero product description, deferring purpose to `IDENTITY.md` via one more hop most readers won't take. `docs/getting-started.md` opens *"This guide is for someone using the suite from a checkout of this repository"* — audience-fit, not purpose; "the suite" has no antecedent in that file. A reader who lands on either doc page directly (plausible via search or a shared link) gets no statement of what Cadre does.

**cadre-kernel** — **has no top-level README.md.** `ls ~/sdk/cadre-kernel` shows only `.git/`, `.github/`, `.gitignore`, `LICENSE`, `Makefile`, `SECURITY.md`, `bin/`, `cmd/`, `go.mod`, `go.sum`, `internal/`, `kernel/` — nothing states what the repository is for. `SECURITY.md`, the first doc a reader would open, is entirely a PyPI-name-collision supply-chain warning. The only purpose-bearing document is one directory down at `kernel/README.md`, and nothing at the repo root points there. `kernel/README.md`'s opening sentence does explain purpose before install — *"This repository is the lifecycle kernel: the G1–G10 gate contracts, mutation-gate definitions, and run-record/agent-catalog/profile/provider JSON Schemas, plus a deterministic CLI — `agentic-sdlc`, a Go binary..."* — but that single sentence front-loads seven undefined terms (G1–G10, mutation-gate, run-record, agent-catalog, profile, provider, overlay) with no glossary anywhere in the repo.

**recall** — `README.md:1-3` opens with title then one purpose paragraph: *"A Go library for building Retrieval-Augmented Generation (RAG) applications. Recall provides structured storage, embedding-based similarity search, metadata filtering, document chunking, persistent SQLite storage, HNSW ANN indexing, and RAG pipeline context assembly — all with zero CGO required."* Purpose precedes commands, but the doc is 1044 lines and the first actionable `## Quick Start` heading doesn't appear until line 36 (3.4% into the file) — everything before it is a 30-bullet feature wall, several bullets running 100-150+ words each. `docs/` has no index file at all (`find ~/sdk/recall/docs -maxdepth 1` returns only `MIGRATION.md` and `BENCHMARKS.md`) — a newcomer browsing that directory gets no orientation toward Quick Start or CLI usage.

**gloop** — `README.md:3` states purpose immediately: *"**Gloop is the orchestration engine behind [cadre](https://github.com/deagy/cadre)**: it executes a governed dispatch plan across agent roles, with streaming, pluggable providers, and per-run monitoring."* Unusually, the doc also corrects its own prior misrepresentation inline (former SDK/MIT-license/pkg.go.dev claims, explicitly disavowed rather than silently dropped). `docs/README.md` is the one genuine, differentiated doc index across all four repos: it states its organizing rule up front — *"Two kinds of document live here, and only one of them describes what runs now. Everything except the four below is a dated record... and each one says so in a banner under its own title"* — then names exactly 4 live files and sections the remaining ~18 historical files by type. The one gap: `docs/PLANNING/` (3 files) is never indexed there at all, so the index's own claim to cover "the documents in this directory" isn't literally true, though the omitted files are all historical-banner-marked so nothing live is hidden.

## Where the trail goes cold

**cadre — primary task: `docs/adopt-cadre-quickstart.md` ("Adopt this suite in a new project, start to finish"), which itself defers to `docs/getting-started.md`.**
- `getting-started.md`'s Prerequisites list `Python 3.10 or newer` — contradicts the repo's own live `REMAINING_PYTHON_SCOPE.md` (*"there is no Python left in this repository. `git ls-files '*.py'` returns nothing"*), confirmed independently (`git ls-files '*.py' | wc -l` → `0`).
- `python3 -m unittest discover -b -s roster/knowledge-store/test -p "test_*.py"` — the directory `roster/knowledge-store/test` does not exist; running the command verbatim fails with `ImportError: Start directory is not importable`.
- `AGENTIC_SDLC_BIN="$PWD/bin/agentic-sdlc"` — `bin/agentic-sdlc` is not a tracked file (`git ls-files bin/` lists no such file); `./bin/agentic-sdlc --version` fails with "no such file or directory".
- *"The kernel's own tests (`kernel/test`)..."* — `kernel/` does not exist anywhere in the checkout at all; the doc talks about it as a known location with no pointer to where the kernel actually now lives (a separate repo, `deagy/cadre-kernel`).
- `adopt-cadre-quickstart.md`'s `cadre schema-validate --routing orchestration/routing.json` — fails as literally given (`open orchestration/routing.json: no such file or directory`); the real file is at `roster/orchestration/routing.json`, and the doc's own path is missing the `roster/` prefix.
- Unstated prior knowledge: `adopt-cadre-quickstart.md` says lifecycle gates are driven by a kernel that *"ships in this repository, so a checkout needs no separate install"* — directly contradicting README.md's own later, bolded *"The kernel is not in this repository"* (see next section). A reader trusting the quickstart's framing and then following getting-started.md's broken `AGENTIC_SDLC_BIN` example hits the failure above with no doc reconciling the two claims.

**cadre-kernel — primary task: `kernel/README.md`'s Install → Initialize → Commands path.**
- `agentic-sdlc --help` claims to print *"the full list"* of subcommands but omits three the doc documents as real, working commands — `provider`, `profile`, `extension` — all three actually work (`agentic-sdlc provider list` returns `null`, exit 0) but are undiscoverable via the doc's own stated discovery method.
- The doc instructs *"Always inspect command-specific help before scripting an interface: `agentic-sdlc --help` / `agentic-sdlc plan --help`"* — tested all 30 documented subcommands with `<cmd> --help`; **27 of 30 fail** with `unknown argument "--help"` (exit 2). Only `detect`, `plan`, `validate`, `show-contract` support it, and the doc's own worked example (`plan --help`) happens to be one of the rare working ones, masking the failure for everything else.
- "overlay" is used repeatedly (lines 45, 61, 74-102) before being defined; the closest thing to a definition is a file-tree listing the reader must reverse-engineer.
- `--classification internal` and `--allow-classification internal` appear in representative invocations with zero explanation of what a classification value is or where valid values are documented.
- "mutation gate" is asserted as a concept with no inline definition — the reader must open `kernel/contracts/mutation-gates.json` to learn what it means.

**recall — primary task: the CLI Quick Start (`recall upload` / `search` / `rag`).**
- Every command and flag the README claims (`upload`, `search`, `hybrid-search`, `rag`, `graph`, `reason`, `store info/migrate/backup/restore`, `cluster status`, `eval`/`eval compare`, `-o`, `--config`, `--server`) matched the built binary's `--help` exactly — the CLI surface itself is accurately documented.
- The gap is upstream of the CLI: the Quick Start's only working example uses `embedder.NewMockEmbedder(384)`, and there is **no stated path anywhere in README.md, ARCHITECTURE.md, CONTRIBUTING.md, or `docs/`** from "mock example" to "first real use with a real embedding provider." README.md's CLI section points only to `deploy/config/` for *"the `cli` section (url, api_key, timeout, output, cluster_nodes)"* — the client-connection config, not `store.embedder`, the setting that actually determines whether search returns anything real. Both shipped example configs (`deploy/config/recall.example.yaml`/`.json`) default `store.embedder.type` to `mock`, so even the "production" example config never demonstrates a real provider end to end.
- The actual instructions for wiring `OpenAIEmbedder`/`CohereEmbedder`/`OllamaEmbedder`/`OnnxEmbedder` exist only in `embedder/README.md`, a per-package README not linked from any top-level doc. `cmd/recall/README.md` (a fuller CLI flags reference) is similarly orphaned.
- `RECALL__SECTION__KEY` env-override format is documented with one worked example (`RECALL__CLI__API_KEY`); the indirection needed to set an embedder's API key via env var (`RECALL__STORE__EMBEDDER__API_KEY_ENV` naming another env var) is never explained or demonstrated.

**gloop — primary task: Quick Start (`gloop dispatch plan.json` / `gloop run orchestration.json` / `gloop status`).**
- All 8 top-level commands and their flags matched the live binary exactly, including the README's own machine-verified `--config` honored/ignored/rejected table for `handoff list`/`get`/`prune` — independently re-run and confirmed identical to the doc's claims.
- The one real defect: README.md's own inline `plan.json` example (lines 466-489), the only self-contained copy-pasteable example in the file, **does not parse.** `"timeout": "10m"` is a string, but `pkg/types/dispatch.go:194,201` declare `Timeout`/`PerRoleTimeout` as plain `time.Duration` (nanosecond integers) with no custom `UnmarshalJSON` anywhere in `pkg/types`, `pkg/dispatch`, or `pkg/govplan`. Copying the block verbatim and running `gloop dispatch <file>` produces `Error: failed to parse plan: json: cannot unmarshal string into Go struct field DispatchPattern.pattern.timeout of type time.Duration`. No other `plan.json` exists anywhere in the repo to fall back on — the only other `*plan*.json` in the tree (`pkg/govplan/testdata/conformance-plan.json`) is a different, incompatible schema (cadre's *governed* plan envelope, not gloop's flat *dispatch* plan).
- `gloop init` is a real, working CLI command never mentioned anywhere in root README.md (only in `docs/ARCHITECTURE.md` and the historical, unindexed `docs/PLANNING/`).
- "cadre" (the plan's producer) is referenced constantly as a prerequisite but explained in exactly one sentence plus a link to a separate private repo the reader has no guaranteed access to; "governed dispatch plan" and "dispatch plan" are used interchangeably despite being structurally different JSON shapes (verified: the governed-plan envelope `{"plan": {...}, "schema_version_at_capture": 8}` vs. the flat dispatch shape `{"task_id", "roles": [...], "pattern": {...}}` gloop actually consumes) with no doc stating they differ.

## Missing entirely

**No document in any of the four repositories states how cadre, gloop, recall, and cadre-kernel relate to each other, or what the intended cross-repo workflow is.** Confirmed by direct search:
- `~/sdk/cadre/README.md` and `~/sdk/cadre/IDENTITY.md` (the suite's own self-description, *"Purpose... What we are... What we are not..."*) never mention `recall` or `gloop` at all.
- `~/sdk/recall/README.md` and `ARCHITECTURE.md` never mention `cadre` or `gloop`.
- No file in any of the four repos is titled or reads as an ecosystem/relationship overview.

What exists instead is a set of scattered, one-directional pointers, each visible only from inside the dependent repo:
- `~/sdk/gloop/README.md:3` — *"Gloop is the orchestration engine behind cadre: it executes a governed dispatch plan across agent roles"* — states the gloop→cadre relationship, but only from gloop's side; nothing in cadre's own docs says gloop exists or that it is the thing that executes cadre's plans.
- `~/sdk/cadre-kernel/kernel/README.md:31-34` — *"This kernel records and validates; it does not drive. ... Dispatching author and reviewer roles and stopping a task at each gate is the caller's job — in practice `cadre` ([deagy/cadre](https://github.com/deagy/cadre)), which asks and lets the kernel answer."* — states the kernel↔cadre relationship, one-directional from the kernel repo.
- `~/sdk/cadre/roster/knowledge-store/README.md:57,94-95` — *"Ingestion now goes through recall,"* and *"The store is recall's; cadre reads it through a governed view. `recall upload roster/knowledge-store/examples/chat-export.json`"* — the one place across all four repos that names the cadre↔recall relationship, buried inside a subsystem README three directories deep, not surfaced from any top-level entry point.
- `~/sdk/gloop/README.md:424` — `[knowledge]  # optional; recall-backed knowledge store` — gloop's own, independent integration point with recall, again undocumented from recall's side.

No document assembles these four fragments into one picture. A team adopting all four repositories would have to independently discover: that gloop is the runtime for plans cadre produces; that cadre-kernel is a separately-versioned dependency cadre consumes for gate/state validation (and is not, despite cadre's own README self-contradiction, vendored inside cadre); and that both cadre and gloop each maintain their own separate, non-cross-referenced integration with recall as a knowledge backend. There is no single adoption-order guide ("install cadre-kernel first, then cadre, then wire gloop as the runtime, then optionally recall for knowledge") anywhere in the four repos.

## Terminology

None of the eight terms asked about has one place, common to all four repos, that a newcomer could read once and be done. The situation differs by term and by repo:

- **roster** — Defined once, cleanly, only in gloop: `docs/ROSTER.md:13-16` — *"An external agent roster is a directory of role definitions (`AGENT.md`), an agent catalog (`catalog.yaml`), and a routing table (`orchestration/routing.json`)."* Cadre, the repo that actually owns and produces rosters, has no equivalent sentence anywhere — `docs/README.md`'s closest approximation is *"Canonical role definitions, policies, routing, workflows, and orchestration contracts live under `roster/`,"* which describes the directory's contents, not the concept, and is absent from `docs/terminology.md`'s own glossary table. cadre-kernel uses "roster" only in five Go source comments (never in any `.md` file), e.g. `contracts.go:8`: *"roster/ asks; the kernel answers"* — treating it as a known sibling codebase without ever stating the equivalence to "cadre" that cadre-kernel's own README states in different words. recall doesn't use the term at all.

- **catalog** — cadre's `docs/terminology.md` defines it cleanly: *"Catalog | [`roster/catalog.yaml`](../roster/catalog.yaml), the machine-readable inventory of role IDs..."* cadre-kernel names "agent catalog" as a JSON Schema (`agent-catalog.schema.json`) but never explains what it semantically contains. gloop defines it differently again, in `docs/ARCHITECTURE.md:55` rather than its README: *"`pkg/catalog/` + `pkg/presets/` | Agent catalog loading/validation... single routing engine."* recall's only "catalog" hits are unrelated PDF-spec jargon (`/Type /Catalog` object) in a test fixture.

- **routing** — Defined in cadre's `docs/terminology.md` via the "Route" row. Explicitly and repeatedly disclaimed in gloop as *not* a gloop concept: `docs/ROSTER.md:8` — *"gloop does not match routes... Route selection and dispatch-plan generation are cadre's."* cadre-kernel mentions `routing.json` as a file name and "provider-owned routing" without ever defining the concept. recall's "routing" hits are all unrelated (HTTP routing, per-document namespace routing, cluster node routing).

- **dispatch plan** — cadre's `docs/terminology.md` gives a real definition (*"A reviewable `cadre select` output identifying matched routes/risks, primary/reviewer/support roles, teams, workflow, required and human gates..."*). gloop defines the same term only informally, by a broken JSON example (see above), never as a field-by-field schema table — and gloop's dispatch-plan shape is confirmed structurally different from cadre-kernel's "governed dispatch plan"/run-record concept, with no doc anywhere stating how the two relate. recall doesn't use the term.

- **gate** — The best-covered term, but still gate-numbering (G1-G10) is nowhere assembled as one table a prose reader would see. cadre's `docs/terminology.md` defines "Quality gate" generically (*"A lifecycle checkpoint (G1–G10) requiring defined criteria and evidence before progression"*) but the individual G1...G10 names live only in `docs/kernel/gate-rationale.md`, unlinked from the terminology page or the doc index. cadre-kernel's only complete table of all ten gate names (G1 Intent, G2 Requirements Baseline, ... G10 Runtime Conformance) exists solely inside the machine-readable `kernel/contracts/lifecycle-gates.json` — no prose document reproduces it. gloop defines "gate" for its *own*, different, simplified approve/reject/skip concept in `docs/ROSTER.md`'s "Quality gates" section, and explicitly states (in a historical, banner-marked doc, `docs/REQUIREMENTS-MAP.md`) that gloop *replaced* the G1-G10 model — a fact invisible to anyone reading only gloop's live docs. recall's "gate" hits are all CI/lock terminology, unrelated.

- **G1-G10** — No single document across all four repos lists all ten gate names in one human-readable place outside a JSON schema file. Everywhere else they're referenced piecemeal by ID (e.g. "G1 Intent," "G2 Requirements Baseline") without the full sequence being reproduced.

- **provider** — Defined consistently but for two unrelated meanings depending on repo, with no doc noting the collision. In cadre/cadre-kernel, "provider" means *"a package that supplies roles, profiles, and extensions to the portable Agentic SDLC kernel"* (cadre `docs/terminology.md`; also `kernel/README.md`'s "Profiles and extensions" section). In gloop, "provider" means an LLM backend — *"Anthropic, OpenAI, Google Gemini, Mistral, Cohere, and a generic HTTP endpoint"* (README.md:20-22) / *"a wire-format adapter behind `types.Provider`"* (ARCHITECTURE.md:93). In recall, "provider" means an embedding backend (OpenAI/Cohere/Ollama/ONNX). Three different concepts, same word, never disambiguated across repos.

- **lane** — Entirely absent from all four repositories. `grep -rn -i '\blane\b'` across `.md`/`.go`/`.json` files in cadre, cadre-kernel, recall, and gloop returns zero real hits in every repo (cadre's only match was in an excluded context-pack directory). Not a term any of these four projects actually uses — there is nothing to find, undefined or otherwise.

- **kernel** — The most confusingly overloaded term. It denotes: (1) the whole `cadre-kernel` repository (*"This repository is the lifecycle kernel,"* kernel/README.md:3); (2) the `kernel/` subdirectory *inside* cadre-kernel, which holds only `contracts/` + a README, while the actual Go implementation lives in `internal/kernel/` outside it — a split the doc itself flags only after the reader has already opened the directory; and (3) a `kernel/` subdirectory cadre's own README describes as still living in-repo (line 56, 71) while the same README's later section says in bold it does not (line ~135) and was deleted at commit `11eefd47`. gloop and recall use "kernel" only in unrelated senses (OS kernel, ONNX compute kernel) or, in gloop's historical docs, as a retired "SDLC Kernel" concept explicitly marked "Not used." No document anywhere disambiguates all three cadre/cadre-kernel senses in one place.
