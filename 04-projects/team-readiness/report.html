What CP-4 found that nothing else did

Deletion evidence lost while the content was already gone

Reproduced with two real processes: delete-ingested removed the chunks, the evidence write lost the lock, and the command exited 1 having left no record. Re-running does not repair it — there is nothing left to delete.

The obvious fix does nothing. The connection string already sets busy_timeout(5000), so the driver spends the whole budget inside the first Exec and the retry loop finds its deadline already expired. A retry whose budget is consumed before its first check is decoration.

A test that could not tell its own mutations apart

The regression test passed with the longer budget removed, passed again with the retry removed entirely, then failed on unmodified code. Three results that cannot all describe the same property.

Chasing the inconsistency exposed the real defect: CREATE TABLE IF NOT EXISTS ran before the INSERT and absorbed the contention, so which statement failed depended only on whether an earlier command had made the table. One mutation would have hidden that; two disagreeing ones could not.

Fixed on the path I changed, not the path the failure takes

Round 2 measured the fix as uneven. A store that had recorded a deletion waited out a competing lock for the full budget and failed at 60.45 s naming the chunk count. A store that never had died at roughly 5 s with a bare SQLITE_BUSY — twelve times shorter, on the more common case, since it is a project's first deletion.

The failing call was in initStagedSchema at store open, a path I had not touched. Creating the table at open removes the case rather than widening a second budget, so no schema change runs after deletion becomes irreversible. Re-verified against cli-v0.7.12: cold now fails at 61.75 s and warm at 60.45 s, and the intermediate durations succeed — which is what distinguishes equalising at the long budget from equalising at the short one.

A guard that could not see the claim it existed to catch

The overview page asserted that a test fails if any document still places the kernel inside cadre. False in both halves: terminology.md still said so, in prose and in a mermaid label, and the guard read only backticked paths and markdown links. A verifier asked to build its own list of syntaxes probed thirty and found six the extended guard still cannot see — recorded as a coverage statement, not hidden.

Open, and needing a person

Not yet proven  AC-1 is verified by a container, not by a colleague

AC-1's own wording makes the container run the automated substitute, and the spec says plainly that it is the confirmation no automated check replaces. The row is correctly graded against the falsification test the criterion states, so this is not a misgraded row — but the north-star's plain sentence says a colleague installs unaided, and no colleague has yet. The gate raised this without being asked to.

Handing the three repositories to an actual person and watching where they stop is the only remaining way to learn what the container cannot tell us.

Blocked in-session  cli-v0.7.10 is a tag with no release

Created by hand before checking that cadre's workflow tags and publishes itself on a version bump, and skips any version already tagged — so the tag both failed to trigger a release and prevented the one that would have happened. It gates none of the releases that actually shipped.

It is not being excepted, because an exception entry would file the mistake as a stated reason. Deleting a remote tag needs human approval: git -C ~/sdk/cadre push origin :refs/tags/cli-v0.7.10
