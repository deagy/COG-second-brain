## On the amendments

**AC-03 (2026-08-28) — clarifying.** The pre-amendment criterion required a *released* kernel to accept a plan, while releasing was P1's own last task: the criterion demanded evidence from after the phase meant to produce it, making it structurally unsatisfiable rather than merely hard. Splitting it kept the fixture property at full rigour (mutation-verified above) and moved the end-to-end run to AC-11 where an installed, released, provider-wired kernel actually exists. Nothing was narrowed away; both halves are still proven.

**AC-04's "no third definition" clause moving to AC-05 (2026-08-28) — clarifying.** The clause depends on `agentic-lifecycle`'s schemas being gone, which is P2's work. It is now verified there, and verified literally rather than generously after a verifier rejected the lead's read-only-cannot-drift argument.

**AC-08 (2026-08-29) — clarifying, and it made the criterion harder.** It went from "every refusal cadre's store makes" to six named refusals pinned to a committed fixture, each requiring a test that fails when its check is removed. The count was corrected upward from five to six when the code was counted rather than the prose read. This is the strongest criterion in the set and the one whose evidence survived the most adversarial re-testing.

**AC-07 (2026-08-29) — easier, and on a premise that is false.** The amendment's stated reason for closing on deprecation rather than removal is: *"gloop is a published Go module — `v0.1.0` and `v0.2.0` tagged, MIT-licensed, on pkg.go.dev, and both functions are exported. Removing them is a breaking change for any importer."* Checked directly: `gh api repos/deagy/gloop` → `"private": true, "license": null`; no `LICENSE` file exists in the tree; the module is not resolvable via the proxy or pkg.go.dev. The tags are real, but a private unlicensed repository has no public importers to break. The amendment relaxed a criterion from "removed" to "deprecated" to protect consumers who cannot exist.

**AC-10 (2026-09-01) — defensible in substance, but amended at the gate.** The reasoning is sound and I falsified its load-bearing claims independently (above). The process is not: `spec.md` was edited at **08:49** today, *after* the 07:19 `CP-3-AC10-dispatch-finding.md` that would otherwise have failed the row, and the P5 ledger rows recording AC-10 verified were written at **08:59**, after both. The spec itself draws exactly this distinction when defending AC-07: *"there, a criterion was read generously at the gate to make failing work pass. Here the criterion was changed before the gate."* AC-10's amendment is the P2 shape, not the AC-07 shape. Structurally it also makes the criterion self-referential — the artefact being judged (the ownership table) is editable by the party being judged, and any duplication can in principle be dissolved by declaring the two implementations two concerns. The recorded reopen conditions are the mitigation and they are real, but the evidence now rests entirely on the quality of a reading rather than on an absence anyone can grep for.

## Weakly verified

Criteria technically satisfied whose evidence would not catch a regression.

- **AC-04 — the drift guard's CI signal is dead.** The guard is genuinely falsifiable (I killed it both ways) but passes locally only because `~/sdk/cadre-kernel` happens to be a sibling directory. On the runner it fails for want of `KERNEL_CONTRACTS_DIR` and has since it was written. A real contract drift would be caught only if someone ran the suite on a machine with the sibling checkout — i.e. by the author, by hand. This is the identical accident the trail already diagnosed and fixed in recall.
- **AC-06 — proven, but unenforced anywhere but this machine.** The conversion property is true and well tested; the two guards that would notice cadre's corpus changing out from under gloop (`TestTheCorpusMatchesCadre`, `TestTheVendoredFixtureMatchesCadre`) are red on every gloop CI run since the feature landed, for want of inputs. gloop's vendored corpus could drift from cadre's tomorrow and nothing outside a local run would say so.
- **AC-08 — the "no query" refusal does not refuse a whitespace query.** Reproduced live: a whitespace-only query passes `govern`'s exact `Query == ""` test, returns a score-0 result and writes an audit row. The refusal test passes because it tests the empty string. The property the refusal exists to hold — that no unqualified query is served — is false for the whitespace case. The ledger and P4 retro both record this honestly as inherited behaviour with a dated action item, but it is written down in neither repository's shipped documentation, only in the vault evidence.
- **AC-08 — one unit test is weaker than it looks.** When cadre's CLI classification check was neutered, `TestKnowledgeSearchMissingClassification` still passed, because a different missing-scope error also returns exit 2 in that test's argument shape. The criterion survives because the CLI contract test (`TestTheCLIRefusesEveryContractCase`) does catch it, but that one narrow unit test would not.
- **AC-11 — the ledger's gate numbers do not reproduce.** The claimed "2 gates standalone (G8, G9) → 9 with the kernel (G1…G9)" did not reproduce for two different real tasks: gate *counts* were identical with and without the kernel wired (8 and 2), and only each gate's `reason` text, `lifecycle_tracking.status` and a provenance field changed. The enrichment mechanism is real — a constructed case with a gap in the declared sequence gave a genuine 6→10 increase — but the specific figures recorded as evidence are not reproducible from anything the evidence file states, because it records no `--task`/`--files` for that run.
- **AC-11 — `SECURITY.md` still points operators at the wrong repository.** cadre's supply-chain section tells a reader to run `./bin/agentic-sdlc --version` (dead command, exit 127), to `gh release download kernel-v<version> --repo deagy/cadre` (wrong repo *and* wrong tag scheme — the real tags are `v0.14.2`), and to verify a `pip show` homepage the same document elsewhere says can never exist. `cadre-kernel` has no `SECURITY.md` at all, so the verification instructions were never carried to the repository that now needs them. `git log -1 -- SECURITY.md` shows it was edited *during* the extraction and left inaccurate.

## Verdict

**FAIL:escalate.** Two of the eleven criteria fail in a way a verifier can fix; two fail in a way only the owner can decide, and the surface area is otherwise strong — AC-01, AC-03, AC-06, AC-08, AC-09 hold up under active mutation testing and are the best-evidenced criteria in the trail.

**Decisions needed (do not close without the owner):**

1. **AC-10, dispatch row.** cadre's `runner="api"` (2,199 lines, real containment) and gloop's `ToolExecutor`/`SessionManager` are, in the finding doc's own words, "two implementations of one thing" — the same ask-endpoint/execute-tool-calls/ask-again loop. AC-10 was closed by amending the criterion to call them two concerns on the grounds that cadre's carries containment gloop's lacks, the same day a finding said the row would otherwise fail, and before the ledger rows recording it verified. The spec's own AC-08 section rejects exactly this argument for an identically-shaped case. Either the runner is retired into gloop carrying the sandbox, allowlist and fence, or the north-star clause ("the losing implementations are deleted or archived rather than left running") is amended at the north-star level to admit this case explicitly — not settled inside an editable table row on the day it was checked.
2. **AC-05, the archived repo's Python implementation.** `agentic-lifecycle` still holds an executable, typed run-record implementation (`lifecycle.py`, `store.py`) at HEAD, missed because the closure inventory searched filenames rather than the concept. Either delete `src/agentic_lifecycle/` (the same operation P2 already performed once for the schemas) or the criterion's "no `run-record` definition exists outside the kernel" needs to say explicitly that a read-only, archived, but still-executable definition is acceptable — it currently doesn't, and the literal wording is unmet.
